# Lecture 02：U+0041 到底是什么？它是怎么“变”出来的？

[课程导航](00-Reading-Guide.md) · 上一讲：[为什么需要 Unicode](01-Why-Unicode.md) · 下一讲：[逐步手算 UTF-8](03-UTF-8-Step-by-Step.md)

**预备知识：** 已理解 Unicode 会为字符分配编号；编号与文件 bytes 不是同一层的东西。

**本讲目标：** 看懂 `65`、`01000001`、`0x41`、`U+0041` 的关系，避免把“改变数字写法”误认为“改变字符编码”。

## 1. 先拿住一个事实：A 的 code point 是数字 65

上一讲已经确认：Unicode 给 `A` 分配的编号是十进制 65。

这个编号可以换一种进制书写，但仍然是同一个数字：

```text
十进制：65
二进制：1000001
十六进制：41
```

这里没有产生三个不同的 code points，也没有把 A 换成另一个字符。

就像“十二”和“12”可以指同一个数量，进制写法改变并不意味着数值改变。

## 2. 01000001 为什么能写成 41？

你已经懂二进制，所以这里只补与编码阅读直接相关的一步：**一个十六进制位，刚好能表示四个 bits。**

把 `01000001` 从右往左，每四个 bits 分成一组：

```text
二进制：0100 0001
          │    │
          ▼    ▼
十六进制： 4    1
```

所以：

```text
二进制 01000001 = 十六进制 41 = 十进制 65
```

用十进制复核：

```text
十六进制 41
= 4 × 16 + 1
= 65
```

常见的误会就在这里：看到 `41`，习惯性地把它读成十进制四十一。但这里的 `41` 是十六进制，要看上下文或前缀。

### 那么 0041 呢？

```text
十六进制 41
十六进制 0041
```

前面加零不改变数值，两者都等于十进制 65。

这不表示小数 `0.041`，也没有小数点。

## 3. U+0041 每一部分在做什么？

`U+0041` 是书写 Unicode code point 的常用形式：

```text
U+  0041
│    │
│    └── 用十六进制写出的编号
└─────── 提示读者：这里写的是 Unicode code point
```

因此，把 `U+0041` 翻成一句完整的话就是：

> Unicode 中，编号为十六进制 0041，也就是十进制 65 的那个 code point。

这个 code point 被分配给字符 `A`。

`U+` 不是参与计算的加号表达式，不表示“U 加上 0041”；它只是标准 notation 的一部分。

常见写法至少保留四位十六进制数字。数字较大时，就会出现五位或六位：

```text
A  → U+0041
中 → U+4E2D
😀 → U+1F600
```

这些编号的长度不同，**不表示 Unicode 临时改变了它们的编号规则**。只是小编号和大编号在书写时需要不同位数。

## 4. 0x41 与 U+0041 有什么不同？

`0x` 是 Java 等语言表示十六进制整数的前缀。

```java
int decimalValue = 65;
int hexValue = 0x41;
```

这两个变量的数值相同，都是整数 65。`0x41` 本身不保证“它一定是一个字符”，也可能是程序里的普通数字。

两种写法强调的事情不同：

```text
0x41：  这个整数使用十六进制写法。
U+0041：我在谈 Unicode 的这个 code point。
```

Java 不能把 `U+0041` 直接当成一个特殊的字符常量语法：它是解释文字中的 code point notation。

后面会遇到另一种写法 `\u0041`。它是 Java source code 中的 Unicode escape，有反斜线、小写 `u` 和四位十六进制数字。它的含义与作用位置会在 [Lecture 05](05-Java-Literals-and-Escapes.md) 单独展开；现在先不要把 `U+0041`、`0x41`、`\u0041` 当成同一种语法。

## 5. 中和笑脸的编号，怎样读成 binary？

这一步仍然只是在表示同一个编号，**还没有进行 UTF-8 encoding**。

### 中：U+4E2D

每一位十六进制数字对应四个 bits：

```text
十六进制： 4    E    2    D
           │    │    │    │
二进制： 0100 1110 0010 1101
```

这里 `E` 表示十进制 14，`D` 表示十进制 13。

因此，以下写法都指相同的编号：

```text
十进制：20013
十六进制：4E2D
二进制：0100111000101101
Unicode notation：U+4E2D
```

### 😀：U+1F600

同样逐位展开：

```text
十六进制： 1    F    6    0    0
           │    │    │    │    │
二进制： 0001 1111 0110 0000 0000
```

这等于十进制 128512。

为了与五位十六进制数字对齐，上面写了 20 个 bits。最前面的零可以省略，因此这个数字本身只需要 17 个有效 bits：

```text
0001 1111 0110 0000 0000
   └──────────────────┘
    1 1111 0110 0000 0000
```

但“表示这个数字最少需要 17 bits”，仍然不等于“UTF-8 文件会只保存 17 bits”。UTF-8 会加入自己的结构 bits，并按完整 bytes 存储，下一讲会逐位算出来。

## 6. “binary 怎么转成 Unicode？”要先确定你手里的 binary 是什么

这个问法可能对应两个不同的问题。

### 情况一：binary 只是 code point 数值的写法

假设已经告诉你：

```text
这串 binary 是一个 Unicode code point 的数值：
01000001
```

那么它就是 65，可以写作 `U+0041`。查 Unicode 的分配关系，知道它是 `A`。

这一步没有 UTF-8 的拆包过程。你只是在换写法，并查这个编号代表什么。

### 情况二：binary 来自文件，表示的是 encoded bytes

假设文件中读到：

```text
11100100 10111000 10101101
```

你不能直接把这 24 bits 连在一起当成一个 Unicode code point。

如果已知它们使用 UTF-8，就必须先按照 UTF-8 规则识别开头和后续 bytes，去掉结构部分，提取真正承载编号的 bits，最后才能得到 `U+4E2D`。

这叫 decode。**同样是 binary，有的在表示一个抽象编号，有的是经过 encoding 组织后的数据。**

下一讲就从这两个层面的区别出发，完整算出上面的三个 bytes。

## 7. 文件里会不会直接保存 U+0041 这几个字？

正常用 UTF-8 保存一个 `A` 时，不会。

```text
要保存的文本：A
UTF-8 bytes：41
```

这里 `41` 是用十六进制展示一个 byte 的值，那个 byte 实际是 `01000001`。

如果你真的在文本编辑器里输入了 `U+0041`，那就是输入了六个字符：

```text
U  +  0  0  4  1
```

用 UTF-8 保存它，得到六个 bytes：

```text
55 2B 30 30 34 31
```

这是“文字内容本身写着 U+0041”，与“保存字符 A”完全不同。

十六进制查看工具显示的 `41`、文档写的 `U+0041`，通常都是帮助人阅读的表示方法，不是文件中自动附加的标签。

## 自测

1. `U+0061` 对应十进制 61 还是 97？为什么？
2. `U+0041` 变成 `U+000041` 会让字符从 A 变成别的字符吗？数值有没有改变？
3. 拿到三个文件 bytes，能不能把它们直接拼成 24 位整数，并断定那就是一个 code point？

<details>
<summary>展开答案</summary>

1. 97。`61` 是十六进制：`6 × 16 + 1 = 97`。对应小写 `a`。
2. 数值没有改变，前导零不改变 65 这个编号。惯常写法是 `U+0041`；强调数值不变，不是建议随意改变 notation。
3. 不能。需要先知道 encoding，并按它的规则判断这些 bytes 表示一个、多个，还是不合法的编码序列。

</details>
