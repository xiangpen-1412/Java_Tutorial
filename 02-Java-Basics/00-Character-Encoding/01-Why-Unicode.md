# Lecture 01：为什么已经有 ASCII，还需要 Unicode？

[课程导航](00-Reading-Guide.md) · 下一讲：[读懂 code point 的写法](02-Code-Points-and-Notation.md)

**预备知识：** 你知道计算机使用二进制，也知道文件能保存数据。这里不重讲进制基础。

**本讲目标：** 分清“给字符分配编号”和“把编号保存成 bytes”这两个问题，理解 Unicode 解决了前一个问题。

## 1. 先只考虑：我要把一个 A 发给另一台计算机

假设你输入了一个大写 `A`，想把它保存到文件，再让另一台计算机读出来。

计算机之间需要一个约定：用什么数字表示 `A`？接收方看到这个数字后，又应该显示哪个字符？

我们暂时自己编一个很小的规则。

> 以下是教学用的假想规则，不是 ASCII，也不是任何真实编码。

```text
假想系统甲的规则：
数字 1 → A
数字 2 → B
数字 3 → C

假想系统乙的规则：
数字 1 → X
数字 2 → Y
数字 3 → Z
```

甲想发送 `A`，于是按自己的规则发送数字 `1`。如果这个数字保存成一个 byte，内容可以是：

```text
00000001
```

乙收到相同的 bits，却按照自己的规则把它理解成 `X`。

```text
甲想表达的字符：A
        ↓ 甲的规则
实际发送的 byte：00000001
        ↓ 乙的规则
乙显示的字符：X
```

这里网络没有丢数据，文件也没有损坏。**真正的问题是：双方使用了不同的解释规则。**

这也是学习文字编码的起点：文件里的 bytes 不会自己告诉你“我一定是一个 A”。你必须知道应该采用什么规则解释它们。

## 2. ASCII 建立了一套统一的编号约定

ASCII 为一组字符和控制符号分配了 `0～127` 的编号。大写 `A` 的编号是十进制 `65`，小写 `a` 是十进制 `97`。

```text
ASCII 约定：

A → 65
B → 66
C → 67

a → 97
b → 98
c → 99
```

`A` 和 `a` 的编号不同，因为它们本来就是两个不同的字符。它们在字母意义上相关，不代表计算机应该把它们存成同一个编号。

现在两台计算机都使用 ASCII，就能建立一致的解释：

```text
发送方：A → 65
接收方：65 → A
```

### 为什么 A 恰好是 65？

这是标准分配的编号。

**不是先分析 A 的形状，再用公式算出 65；也不是先有 A 的二进制，再从二进制创造出字符编号。**

你可以把它理解成登记表中的对应关系：查表知道 `A` 对应 `65`，然后才考虑怎样表示和保存 `65`。

这个编号体系有设计历史，但日常 Java 编程不需要推导“为什么设计者把 A 放在 65”。需要知道的是：程序共同遵守了这个对应关系。

### 7 bits、8 bits、byte 分别在说什么？

这里先纠正一个容易把后面全部带偏的单位问题：

```text
1 byte = 8 bits
2 bytes = 16 bits
4 bytes = 32 bits
```

ASCII 的编号只需要 7 bits，因为 `0～127` 一共有 128 种可能。

但在现代常见的按 byte 保存的文件中，一个 ASCII 字符通常用一个 byte 表示，最前面补一个 `0`：

```text
A 的编号 65：

7 bits： 1000001
1 byte：01000001
```

补零没有改变编号，仍然是 65。

## 3. ASCII 的问题：它能登记的字符太少

如果文件里只有英文字母、基本标点和数字，ASCII 可以处理很多需求。

但现在你想保存：

```text
café
中文
😀
```

ASCII 没有给这里的 `é`、汉字和笑脸分配编号。因此，单靠 ASCII 无法表示这些文本。

不同地区、语言和系统于是使用了其他规则。你可能见过 GBK、Big5、Shift_JIS、Windows-1252 这些名称。它们的细节放在附录，这里只需要理解当时的问题：

**如果每套规则都只覆盖自己的字符，而且彼此的 byte 对应关系不同，交换文本时就必须先知道对方用了哪一套。**

回到本讲开头：同一串 bytes，用不同规则读，有可能变成不同文字；某些字符甚至在接收方规则中根本不存在。

## 4. Unicode 先统一“字符对应哪个编号”

Unicode 建立了一套覆盖多种语言和符号的统一标准。它给字符分配的编号，叫 **code point**。

这讲先不引入新的编号写法，就使用你已经熟悉的十进制：

| 字符 | Unicode 为它分配的编号，十进制 |
|---|---:|
| `A` | 65 |
| `a` | 97 |
| `é` | 233 |
| `中` | 20013 |
| `😀` | 128512 |

这张表的每一行回答的是：**“这个字符在统一编号体系里的号码是什么？”**

它还没有回答“保存到文件时会占几个 bytes”。

### 为什么 A 在 Unicode 里仍然是 65？

因为 Unicode 保留了 ASCII 中的字符和对应编号。ASCII 的 `0～127` 被原样纳入 Unicode。

因此：

```text
ASCII 中： A → 65
Unicode 中：A → 65
```

我们可以说 ASCII 的字符及其编号是 Unicode 的一个子集。

这不等于“所有 Unicode 编码的文件都与 ASCII 使用完全相同的 bytes”。字符编号是否相同、最终 bytes 是否相同，仍然是两个问题。

## 5. 编号统一以后，为什么还需要 UTF-8、UTF-16？

因为文件和网络最终处理的是 bytes。**“大家都同意 A 的编号是 65”还不等于“大家都同意怎样把 65 写进文件”。**

即使只是保存数字 65，也可以设计不同的格式：

```text
占一个 byte：
01000001

占两个 bytes，先放高位：
00000000 01000001

占四个 bytes，先放高位：
00000000 00000000 00000000 01000001
```

三种形式都能承载数字 65，但文件大小和读取规则不同。接收方需要知道到底应该一次读一个、两个，还是四个 bytes。

再考虑 `😀` 的编号 128512：一个 byte 装不下。应该拆成几块？每块保存哪些 bits？读取时怎样知道这些 bytes 属于同一个 code point？

这才是 UTF-8、UTF-16、UTF-32 要具体规定的事情。

这一阶段可以这样分工：

```text
Unicode 的字符分配：
😀 对应编号 128512。

某一种 UTF encoding：
这个编号按什么规则变成可保存的数据单位。
```

严格说，Unicode 标准本身也定义这些 encoding forms 以及更多文本规则。我们在学习时先把“编号”与“编号如何表示”拆开，是为了不把它们混在一起。

## 6. 先把两种转换的名字放到已经理解的过程上

现在才引入两个名字，不需要先背定义：

```text
知道要表达的字符和编号
        ↓ 按指定 encoding 生成 bytes
      文件中的 bytes
```

向下这一步叫 **encode**。

```text
      文件中的 bytes
        ↓ 按指定 encoding 还原编号和文本
知道表达了哪些字符
```

向下这一步叫 **decode**。

所以“按 UTF-8 decode 文件”就是说：按照 UTF-8 的规则拆解文件中的 bytes，恢复文本。下一讲先读懂这些编号的常见写法，第三讲再真正手算 UTF-8 的规则。

这里讲的是 Java 后续要处理的数据概念，不是 JavaScript；目前也还没有开始讲任何 Java API。

## 自测：先解释原因，再看答案

1. `A` 的编号 65 是从它的形状计算出来的吗？
2. `8 bits` 是几个 bytes？`16 bits` 呢？
3. 已经知道 `😀` 的 Unicode 编号，是否就能在不知道 encoding 的情况下，断定文件里会是哪几个 bytes？

<details>
<summary>展开答案</summary>

1. 不是。编号来自标准约定的分配关系。之后可以对这个编号进行数值表示和编码计算。
2. `8 bits = 1 byte`；`16 bits = 2 bytes`。
3. 不能。还要知道采用 UTF-8、UTF-16 或其他哪一种 encoding，以及某些格式所需的 byte order。
