## 2. 350、383 的共同模型：把频次当作可消耗状态

单纯统计次数只是第一步。更可复用的理解是：

```text
frequency[key] = 当前还剩多少个 key 可以使用
```

状态变化统一为：

```text
遇到供应 → frequency[key]++
完成一次匹配或遇到一个需求 → frequency[key]--
```

频次表因此不仅回答“总共出现过多少次”，还可以回答“现在还能不能再使用一次”。

这个模型成立的原因是：每一次具体出现的元素只能参与一次匹配。成功使用后减少频次，就能防止同一个资源被重复使用。

## 3. 两题的同与不同

| 对比项 | 350 | 383 |
| --- | --- | --- |
| 供应 | 任选一个数组的元素 | `magazine` 中的字母 |
| 扫描对象 | 另一个数组 | `ransomNote` 的需求 |
| 库存大于 0 | 把元素加入交集并减一 | 当前需求可以满足并减一 |
| 库存不足 | 跳过当前元素 | 整体立即失败 |
| 目标 | 收集所有成功匹配 | 验证是否全部满足 |

350 允许某些元素匹配失败，因为它只返回交集；383 不允许任何需求失败，因为它要求构造完整字符串。

## 4. 存在性与频次必须分清

这组题真正训练的是“到底要保存什么信息”：

```text
只问出现过没有、结果需要去重
→ Set / boolean 状态

问出现了几次、还能使用几次
→ frequency
```

第 349 题只需要存在性；第 350 题必须保留重复配对次数；第 383 题必须判断供应数量是否覆盖需求数量。题目中的“只能使用一次”“保留出现次数”“数量是否足够”都是频次模型的识别信号。

## 5. 数组哈希与 HashMap 的选择

频次关系在概念上是：

```text
key → count
```

具体结构由 key 的范围决定：

| key 的条件 | 优先结构 | 原因 |
| --- | --- | --- |
| 范围很小、连续、已知 | 计数数组 | key 可以直接变成下标，常数开销小 |
| 范围很大、有负数或未知 | HashMap | 只保存真正出现的 key，不需要覆盖整个值域 |

350 和 383 都给了适合直接寻址的范围：

```text
350：整数在 0～1000 → 1001 个计数位置
383：字符在 a～z → 26 个计数位置
```

数组哈希没有真正计算 hash，但它和 `Map<key, count>` 表达的是同一种映射关系。

454 的两数和取值范围较大且可能为负，实际配对最多只有 `n²` 组，使用 HashMap 只记录真正出现的和更合适。负数本身并不排除计数数组：若值域仍然很小，可以通过偏移量映射下标；关键是完整值域所需的空间是否合理。

## 6. 从初始解法得到的优化经验

### 不必为两边都建立完整频次表

350 最初为两个数组分别建立 HashMap，再对共同 key 取最小值。它是正确的，但可以把一边统计为库存，扫描另一边时即时消耗。第二边不需要完整保存。

### 固定范围优先考虑直接寻址

当题目明确给出很小的连续值域时，先问：

```text
这个值能否直接成为数组下标？
```

如果可以，计数数组通常比包装类型 HashMap 更直接。

### 分析空间时要计算辅助副本

383 的频次表只有 26 个位置，但 `toCharArray()` 会另外复制整个字符串。数据结构是固定空间，不代表完整实现自动就是固定额外空间。

## 7. 454：从重复枚举变成配对数量查询

将四数相加拆成两半：

```text
a + b + c + d = 0
c + d = -(a + b)
```

固定前两个数后，原来的内层循环在反复回答“后两个数组中有多少对元素的和等于所需值”。可以先统计后两个数组全部配对的和，再为每个前半组查询一次。

```text
key   = 后半组的两数和
value = 产生这个和的下标配对数量
```

如果需要的和有 3 种配对，当前前半组选法就贡献 3 个四元组。不同前半组选法可以复用同一份后半组统计，查询后不减少频次。

复杂度变化来自两部分执行关系的改变：

```text
原来：n² 种前半组 × n² 种后半组 = n⁴
现在：预处理 n² + 枚举并查询 n² = 平均 O(n²)
代价：最坏 O(n²) 额外空间
```

HashMap 查询是平均 `O(1)`，不是“无限趋近于 `O(1)`”。后半组的枚举被统一提前执行一次，原来的重复搜索才得以省去。

| 频次的含义 | 代表题 | 后续怎样使用 |
| --- | --- | --- |
| 剩余资源数量 | 350、383 | 使用一次，减少一次 |
| 可行配对数量 | 454 | 查询后加到答案，可以反复复用 |

## 8. 通用推导流程

以后遇到相似题，可以按顺序问：

```text
1. 我只关心元素存在，还是关心出现次数？
2. 每个元素能否被重复使用？
3. frequency 表示剩余资源，还是可复用的选法数量？
4. 能否只统计一边，扫描另一边时即时消费或查询？
5. key 的范围是否足够小，可以直接用数组下标？
6. 某次消费失败时，是跳过，还是整个问题立即失败？
7. 多层循环的内部是否反复回答同类问题，可以预处理答案？
```

第 6 个问题区分了 350 与 383：

```text
求交集 → 匹配失败可以跳过
满足全部需求 → 任一次失败都代表整体失败
```

## 9. 记忆主线

```text
存在性       → Set / boolean
确定过程判环 → 记录完整状态
分区域去重   → 各区域分别维护出现记录
重复次数     → frequency
范围小且连续 → 数组直接寻址
范围大或未知 → HashMap
消耗资源     → 频次减一
统计组合     → 查询频次并累加，不消耗
多组求和     → 尝试折半枚举，查询补数
求部分匹配   → 没库存就跳过
要求全部满足 → 没库存就失败
```

## 10. 本轮补记：202 与 36

### 202：记录状态，同时辨别真正需要存多少数据

`new int[n]` 把整数的数值当成了数位数量，十位数可能因此申请数十亿个位置。拆位后只需要平方和，可以取出一位就累计，无需存数组。

HashSet 记录的是每轮的完整数字。相同数字一定转到相同后继，所以状态重复足以确认循环。快慢指针也能利用这个固定后继关系判环，省掉访问历史；原来的 Set 思路本身正确。

### 36：将重复搜索转成区域内的存在性查询

一行、一列、一个宫格各自维护出现记录；后遇到的重复数字会查到先前的记录，无需对每个数字重新搜索整个区域。

宫格遍历要先解释坐标意义：

```text
宫格行列 i、j，内部偏移 x、y：
row = i * 3 + x
col = j * 3 + y
```

原先的 `x * (i + 1)` 改变了访问间隔，而正确关系是“区域起点 + 内部偏移”。编号除以区域宽度、对宽度取余，可以把两组二维坐标分别压成一维编号，进而复用两层循环。循环更少不代表工作量更少：四层各 3 次和两层各 9 次都是 81 次访问。

字符类型、自动装箱及比较方法与状态、坐标推导一起保存在 [[08-36 - Valid Sudoku]]，方便结合题目复习。

## 11. 128：状态必须真正阻止重复搜索

自己的方案是从任意未处理数字向两边查找相邻整数，并把整段标记到 visited。它不要求先找到全局最小值，也不需要统计频次；HashSet 只需回答“数字是否存在”。

两次实现中暴露的关键问题：

- 只添加 visited，却没有在外层查询并跳过，仍会从每个数字搜索整段。
- 加了跳过判断，但漏掉起点自身的标记；例如 `[1, 1, 1, 2, 3, 4]` 中，三个 `1` 都会触发整段搜索。起点和向两边找到的数字都要标记，重复起点才能被跳过。

完整标记后，每个连续段只展开一次。所有段的不同数字数量之和不超过 `n`，所以所有 while 的工作量加起来是平均 `O(n)`，加上建集合和外层扫描，总时间仍是平均 `O(n)`，最坏额外空间为 `O(n)`。

**循环嵌套不自动意味着复杂度相乘；要看每轮是否重复做同一批工作。** 另一种方式是仅从没有前驱的数字出发，遍历去重集合并向上扩展，同样保证每段只处理一次。

128 的复盘重点是“记录 → 查询并跳过 → 标记覆盖完整 → 计算总工作量”。第二版截图虽然通过测试，漏标起点时仍可能退化到平方级；具体过程见 [[10-128 - Longest Consecutive Sequence]]。

## 12. 1657：从允许的操作推导不变量

位置交换允许重排字符，整体交换两种已有字母允许交换它们的次数；两种操作都不能引入新字母，也不能改变频次的多重集合。

最初只想到排序比较频次，认为具体字母不重要。反例是 `cabbba` 与 `eddfff`：频次都为 `[1,2,3]`，但字母种类不同，不能转换。修正后需要同时比较：

```text
出现过的字母集合相同
排序后的频次相同，必须保留重复频次
```

这两个条件也足够：先整体交换字母，使各字母获得目标次数，再交换位置排成目标字符串。

Map 实现可比较 `keySet()`，把 `values()` 复制进 List 后排序比较。不能把频次放进普通 Set，否则 `[1,1,2,3,3]` 与 `[1,2,2,2,3]` 都变成 `{1,2,3}`，会丢失必要信息。

只有 26 种字母时可用 `int[26]` 减少统计的常数开销。先检查相同下标的存在性，再排序频次数组；排序后下标已失去字母身份。List 最多只有 26 项，排序不是主要的大规模工作，Map 版本平均时间本来就已是线性的。

相关 Map 视图、Set/List 相等比较、Comparator 和数组比较 API 都随题保存在 [[11-1657 - Determine if Two Strings Are Close]]。

## 13. 554：统计缝隙，不是逐条竖线扫描砖块

每行的内部前缀和表示砖缝位置。用 Map 统计同一位置在多少行出现，穿过砖块的最少数量就是“总行数减去最多对齐的砖缝数”。不能记录整面墙的右边界，也不能用 Set 去重相同的行，否则会丢失行数贡献。

单块砖的宽度能放进 int，不代表累加位置也能。位置与 Map 的 key 应使用 long / Long，次数仍可用 Integer。详见 [[12-554 - Brick Wall]]。

## 14. 705：从使用哈希表，到自己维护哈希表

用桶数组定位，再用链表区分冲突元素。下标相同不代表 key 相同，桶定位是常数时间，桶内扫描却取决于链表长度。

这轮实现的主要复盘点是：

- 查询用 `current != null` 检查包括尾节点在内的所有节点，并推进指针。
- 插入前去重；修好查询后，可能暴露原先被掩盖的重复插入问题。
- 删除时先执行 `prev = current`，再推进 `current`，只绕过目标节点。
- 固定 15 个桶不能保证操作始终是平均常数时间。

完整的错误示例、节点关系与边界自测见 [[13-705 - Design HashSet]]。

## 15. 149：先定义等价关系，再设计 key

固定一个基准点后，相同斜率表示同一条直线，Map 统计该方向上的其他点数，结果再加基准点自身。换基准点就清空 Map；否则同斜率但位置不同的平行线也会被混在一起。只有一个点时，虽然 Map 为空，答案仍为 1。

这次的两种 key 错误方向相反：

- 用整数除法计算斜率，把 `1/2`、`1/3` 都变成 0，本来不同的方向被错误合并。
- 改成 `double` 后，水平线两侧可能产生 `0.0`、`-0.0`，数学上相同的方向却被分成两个 `Double` key。

最小修正是先进行浮点除法，再把零统一成正零。更精确的表示是用 GCD 约分 `(dy,dx)`，并统一符号，让水平线、竖直线分别变成 `(0,1)`、`(1,0)`。关键并非记住某个容器，而是让程序中的 key 相等关系符合题目中的“属于同一组”。

只遍历 `j > i` 能省掉 visited：任意一组共线点中，下标最小的点作为基准时已经可以统计完整。算法仍枚举平方级点对，优化主要减少重复扫描、对象创建和查表。GCD 的价值在精确表示，不保证每次提交都比浮点版本更快。

GCD 为什么保持公约数、`1071` 与 `462` 的完整求余过程、方向规范化和复杂度见 [[14-149 - Max Points on a Line]]；除法转换与 `Double` 正负零比较规则见 [[10-Integer Division & Double Keys]]。
