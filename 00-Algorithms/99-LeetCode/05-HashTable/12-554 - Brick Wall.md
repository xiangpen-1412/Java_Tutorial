# LeetCode 554：Brick Wall（砖墙）

> 难度：Medium  
> 主题：前缀和、HashMap 计数、最小穿砖转最大接缝、整数溢出

## 1. 问题

`wall` 是一个 `List<List<Integer>>`，每个内部列表表示一行，每个整数表示一块砖的宽度。每行砖块数量可以不同，但总宽度相同，所有砖宽均为正数。

在墙内部选一个水平位置，从上到下画一条固定位置的竖直线。穿过砖内部计为穿过一块砖，沿两块砖的接缝通过则不计。不能沿整面墙的左、右外边缘画线，也不能逐行拐弯。

要求返回最少穿过的砖数，而不是画线位置或被穿过砖的宽度。

## 2. 从逐个尝试位置到只关注接缝

最初的想法是：墙宽为 6，就尝试内部位置 `1～5`，逐行计算各条线穿过几块砖，再取最小值。这里的 6 是总宽度，不是砖块数量。

这种方法的问题是墙宽可能很大，而砖的数量相对很少。大片砖内部的不同位置不会提供更好的结果；真正能让某行少穿一块砖的，是这一行的内部接缝。

因此先把砖的宽度转换成接缝位置。前缀和表示从左边开始的累计宽度：

```text
一行砖：[1, 2, 3]
累计宽度：1、3、6
内部接缝：1、3
```

最后一个累计值 6 是右外边缘，必须排除。前缀和在这里用于确定位置，无需保存完整前缀和数组，只维护一个累计变量即可。

## 3. 核心转换：穿砖最少，就是对齐的内部接缝最多

固定一条竖线后，每一行只有两种情况：经过接缝，避开砖；或者经过砖内部，穿过一块砖。

因此：

```text
某位置穿过的砖数 = 总行数 − 在该位置有内部接缝的行数
最少穿砖数 = 总行数 − 同一内部接缝位置的最大出现次数
```

例如：

| 一行的砖宽 | 内部接缝位置 |
| --- | --- |
| `[1,2,3]` | 1、3 |
| `[3,1,2]` | 3、4 |
| `[1,3,2]` | 1、4 |

位置 1、3、4 各出现两次。任取其中一个位置，能避开两行的砖，因此最少穿过 `3 − 2 = 1` 块。

要找的是出现次数最大的那个位置，不是数值最大的那个位置。其余从未成为接缝的位置会穿过所有行，无需逐个枚举。

## 4. Map 的 key 和 value 分别是什么？

```text
key   = 从墙左边量起的内部接缝位置
value = 有多少行在该位置存在接缝
```

每行从零开始累加，处理到倒数第二块砖为止；每得到一个内部接缝，就把对应计数加一。砖宽为正，因此同一行的接缝位置严格递增，一个位置在同一行中最多被记录一次。这保证“出现次数”正好等于“对应行数”。

最后查找最大计数，再用总行数减去它。也可以在更新计数时同步维护最大值，省去最后遍历 Map；两种写法的渐进复杂度相同。

这道题归入 HashTable，组合使用了前缀和与频次统计：前缀和生成可查询的位置，HashMap 统计相同位置的贡献。

## 5. 最初记录接缝时遇到的两个问题

### Set<List<Integer>> 会错误地合并不同的行

两行都是 `[1,2,3]` 时，各自的接缝列表都是 `[1,3]`。放进 Set 后只剩一份，但两行都应该为位置 1、3 各贡献一次。

如果分两阶段保存接缝，外层应使用 `List<List<Integer>>` 保留每一行。最终实现可以直接把接缝计入 Map，省掉中间列表。

### 不应无条件记录第一块砖的结束位置

原先先执行 `sum.add(list.get(0))`，遇到单块砖的一行 `[6]` 就会把右外边缘 6 当成接缝。

统一规则更可靠：从累计位置 0 开始，只处理最后一块之前的砖。单块砖的行自然不产生任何内部接缝。

如果所有行都只有一块砖，Map 为空，最大接缝次数按 0 计算，答案就是总行数。最大次数因此应初始化为 0。

## 6. 最后一个测试失败：累计宽度超出了 int

提交通过 88/89 个测试，但下面的输入返回 0，正确答案是 1：

```text
第一行：[1, 2147483647, 2147483647, 3]
第二行：[2147483647, 2147483647, 3, 1]
```

正确的内部接缝为：

```text
第一行：1、2147483648、4294967295
第二行：2147483647、4294967294、4294967297
```

没有共同的内部接缝，所以最多避开一行，答案为 `2 − 1 = 1`。

Java 的 `int` 最大值是 `2147483647`。使用 `int position` 累加时不会自动扩大类型，也不会因普通整数加法溢出而抛出异常，而是产生回绕后的错误值：第二行的 `4294967297` 变成了 `1`。

它与第一行真实的接缝位置 1 使用了相同 Map key，于是被错误地计为两行对齐，得到 `2 − 2 = 0`。这是计算结果溢出造成的错误键，不是 HashMap 本身的冲突处理问题。

修正时，累计变量和 key 类型必须一起扩大：

```java
Map<Long, Integer> map = new HashMap<>();
long position = 0;
```

后续若遍历 `map.keySet()`，循环变量也应是 `Long`。value 记录行数，最大计数与返回值仍可用 `int`。

只在累加完成后把结果强转为 long 无法补救，因为之前的信息已经丢失。让累计变量从一开始就是 long，才能在每次加法中使用足够大的范围。

这次应记住的判断是：**单个输入值能放入 int，不代表多个输入的和也能放入 int。选类型要看中间结果的范围。**

## 7. 复杂度与可迁移的收获

设总砖数为 `B`，不同内部接缝位置有 `U` 个。处理所有行并统计接缝的平均时间为 `O(B)`，最后查找最大值为 `O(U)`；由于 `U <= B`，总平均时间为 `O(B)`，辅助空间为 `O(U)`，最坏为 `O(B)`。

性能依赖砖的数量，而不依赖总宽度。每行长度不同，不能仅看有两层 for 就直接说成 `O(n²)`，应计算所有行实际处理的砖数之和。

可以迁移到其他题的思路：

- 连续位置范围很大时，寻找真正改变结果的边界，而非逐点尝试。
- 求最少损失时，考虑能否改成求最多避开或保留的数量。
- 输入给出每段长度时，用累计和恢复各段边界的位置。
- 多个对象都在同一个位置贡献一次时，用“位置 → 贡献次数”统计。
- 如果变种需要返回画线位置，可在最大计数更新时同时记录对应 key；如果允许贴墙边画线，原题排除外边缘的规则就不再成立。
