# 705. Design HashSet：桶定位与链表维护

## 1. 题意与分类

不能使用内置哈希表库，自己实现一个保存整数的集合：

- `add(key)`：加入元素；已经存在时不能重复加入。
- `contains(key)`：判断元素是否存在。
- `remove(key)`：删除元素；不存在时什么也不做。

`key` 范围是 `0` 到 `10^6`，三个操作合计最多调用 `10^4` 次。题面没有明确要求每次操作必须是 `O(1)`。

分类：**数据结构设计 → 哈希表 → 链地址法处理冲突**，同时练习单链表的查找、插入、删除。

## 2. 从数组定位，到桶内查找

自己的思路是用 `Node[]` 保存桶入口，再用链表保存落在同一个桶里的元素，这个方向正确。

但哈希值、桶下标不保证独一无二。例如用 `key % 15`：

```text
12 % 15 = 12
27 % 15 = 12
42 % 15 = 12

set[12] → 12 → 27 → 42 → null
```

这三个不同元素落在同一个桶里，叫哈希冲突，不是重复元素。桶里仍要保存原始 `key`，并逐个比较值。

因此查找分两步：**先通过下标定位桶，再在桶里寻找目标**。数组下标访问是 `O(1)`，不代表整个查找都是 `O(1)`。

`new Node[15]` 只创建引用数组，每个位置最初是 `null`，不会自动创建 15 个节点。

## 3. 是否需要虚拟头节点

两种设计都可以，当前实现使用的是“没有虚拟头节点”的版本：

- 空桶为 `null`，桶入口直接指向第一个真实元素。
- 删除头节点时，必须更新 `set[bucket]`。
- 删除其他节点时，修改前驱节点的 `next`。

如果改用虚拟头节点，它不代表集合中的元素，查找要从它的 `next` 开始。它能统一删除逻辑，但不是必需，不能把两种设计的起点混用。

单链表节点只需要 `val` 和 `next`。删除时的 `prev` 可以是方法里的临时变量，不必给每个节点增加一个前驱字段。

## 4. contains：检查当前节点，而不是检查它有没有后继

`hasNext()` 返回 `next != null` 本身没有错，但它回答的是“后面还有节点吗”，不是“当前节点存在吗”。

最初写 `while (current.hasNext())` 有两个问题：

1. 只有一个节点时，循环根本不执行；尾节点也永远不会被检查。
2. 循环里没有推进 `current`，遇到不匹配且有后继的节点时会一直停在原处。

遍历所有真实节点的基本结构是：

```java
while (current != null) {
    // 检查 current.val
    current = current.next;
}
```

记住：**循环条件决定哪些节点会被检查，指针推进保证遍历能够结束。**

## 5. add：集合必须去重

最初直接把新节点接到尾部，没有判断是否已经存在：

```text
add(1) → add(1)       桶里实际变成 1 → 1
remove(1)            删除一个后仍剩下 1
contains(1)          得到 true，但集合语义要求 false
```

修好 `contains` 后出现这个错误，不是修复引入了问题，而是正确的查询暴露了原先的重复插入。旧查询会漏掉剩下的单个节点，可能暂时掩盖这个错误。

加入前先判断是否存在，可以保证正确性。新节点应在确定需要插入后再创建，避免重复添加时白创建对象。

先调用 `contains` 再找尾节点，会扫描同一个桶两遍；之后可以把去重与定位尾节点合并，或去重后使用头插。这是常数优化，不应先于正确性。

## 6. remove：prev 必须随 current 一起移动

最新版本虽然声明了 `Node prev = null`，但遍历时只移动 `current`，从未更新 `prev`。结果每次删除都进入“删除头节点”的分支。

例如删除 27：

```text
原来：set[12] → 12 → 27 → 42
错误：set[12] → 42             12 也被丢失了
正确：set[12] → 12 → 42        只跳过 27
```

查找时需要维持的关系是：`prev` 始终指向 `current` 的前一个节点。

```java
while (current != null && current.val != key) {
    prev = current;
    current = current.next;
}
```

顺序不能反过来：先记住当前节点，再向后走。找到目标后：

- `prev == null`：目标是头节点，让桶入口指向 `current.next`。
- `prev != null`：让 `prev.next` 指向 `current.next`，保留前面的链表。

最初版本还会对空桶调用 `hasNext()`，或在没找到目标时仍执行删除。后来加入 `if (!contains(key)) return;`，解决了空桶和不存在目标的保护，但不能替代维护 `prev`。

进一步可以只查找一遍：循环结束后若 `current == null` 就返回，否则再删除。不要在确认节点存在之前访问 `current.next`。

## 7. 复杂度：固定 15 个桶不等于常数时间

设集合有 `s` 个元素、`B` 个桶，目标桶链表长度为 `k`：

- 定位桶：`O(1)`。
- 查询、去重插入、删除：最坏需要扫描目标桶，`O(1 + k)`。
- 分布均匀时，平均桶长约为 `s / B`，操作期望为 `O(1 + s / B)`。
- 所有元素落在同一桶时，操作退化为 `O(s)`。
- 总存储空间：`O(B + s)`。

当前 `B = 15` 固定不变，元素增加时链表会变长，不能直接说操作平均永远是 `O(1)`。通常所说的哈希表平均常数时间，需要合理的分布和负载控制；增加桶数、按负载扩容都是后续方向。

本题还有利用有限值域直接记录存在性的做法，但那是另一种空间取舍。当前链地址法更适合练习真实的冲突处理。

## 8. 自测与复用

优先测试这些小场景，比只看复杂失败输入更容易定位错误：

- 空集合查询、删除：返回 false 或不操作。
- 加入同一个值两次，再删除一次：该值应不存在。
- 加入 `12、27、42`：三者冲突，但都应能查到。
- 分别从上述链表删除头、中间、尾节点：其他值应保留。
- 删除同桶里不存在的 `57`：不能影响 `12、27、42`。
- 边界值 `0` 和 `1000000`：仍能正常加入、查找和删除。

复习核心：**桶下标不是唯一身份；集合要去重；遍历检查当前节点；删除要保持前驱关系。** 这些原则也适用于设计 HashMap：冲突时仍按 key 查找，只是节点还要保存 value，并在重复 key 时更新 value。
