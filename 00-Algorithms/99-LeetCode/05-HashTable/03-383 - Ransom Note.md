# LeetCode 383：Ransom Note

> 难度：Easy  
> 主题：字符频次、数组哈希、资源供需、库存消耗

## 1. 问题

给定字符串 `ransomNote` 和 `magazine`，判断能否只使用 `magazine` 中的字母构造出完整的 `ransomNote`。`magazine` 中每一次具体出现的字母只能使用一次，字符原来的顺序不重要。

对任意字母 `c`，都必须满足：

```text
count(ransomNote, c) <= count(magazine, c)
```

只要有一种字母的需求量超过供应量，就应该返回 `false`；所有字母都满足才返回 `true`。

题目保证两个字符串只包含小写英文字母，长度最大为 `100000`。

## 2. 这份解法属于什么类型？

当前使用 `int[26]` 的方法属于：

```text
哈希思想
→ 数组哈希 / 直接寻址
→ 字符频次统计
→ 资源库存与消耗
```

它虽然没有创建 `HashMap`，但 `int[26]` 承担的仍然是映射职责：

```text
key   = 字母
value = 该字母当前剩余的数量
```

因为 key 的范围固定为 `a～z`，可以通过 `character - 'a'` 把它直接映射到 `0～25`，数组比 HashMap 更合适。

## 3. 当前方法的逻辑

当前方法分为三个阶段：

```text
1. 遍历 magazine，对相应字母增加库存
2. 遍历 ransomNote，对相应字母消耗库存
3. 检查 26 个位置中是否出现负数
```

例如：

```text
ransomNote = "aabc"
magazine   = "abbacc"
```

统计 `magazine` 后：

```text
a → 2
b → 2
c → 2
```

依次消耗 `ransomNote`：

```text
需要 a：2 → 1
需要 a：1 → 0
需要 b：2 → 1
需要 c：2 → 1
```

所有库存都没有变成负数，因此供应能够覆盖全部需求。

如果还需要一个 `a`：

```text
a：0 → -1
```

负数表示需求量已经超过供应量，因此无法构造。

## 4. 核心不变量

处理完 `ransomNote` 的某个前缀后：

```text
frequency[c]
= magazine 中 c 的总供应量
- 已处理需求中 c 的消耗量
```

因此数组中的值表示的不是原始出现次数，而是**剩余库存**：

- 大于 `0`：还有多余字符；
- 等于 `0`：恰好用完；
- 小于 `0`：当前字符供不应求，已经能够确定失败。

正是这个不变量保证了“增加供应、减少需求、检查负数”的判断成立。

## 5. 为什么是 int[26]，不是 HashMap 或 char[26]？

### 与 HashMap 的比较

这题的字符集合固定、连续且很小：

```text
a～z，共 26 种
```

所以可以直接通过字符计算下标。数组和 HashMap 的理论扫描时间都是线性的，但数组没有哈希计算、对象节点及装箱拆箱，结构也更能直接表达固定字母表。

如果题目改成范围很大或未知的符号集合，固定 26 位数组就不再适用，届时才考虑 Map。若需要正确处理超出 BMP 的 Unicode 字符，还要按 code point 遍历，不能简单地把每个 Java `char` 都当成一个完整字符。

### 为什么计数不能用 char[26]

`char` 可以转换成整数，是因为它保存的是一个 `0～65535` 的 UTF-16 编码单元；但这里要保存的是出现次数，而不是字符编码。

本题字符串长度最多为 `100000`，同一个字母的频次可能超过 `65535`。使用 `char` 计数会有溢出风险，使用 `int` 才能安全表达这个数量。

角色应当分清：

```text
char：当前读到的是哪个字符
char - 'a'：这个字符对应哪个下标
int：该字符还有多少库存
```

## 6. 当前实现还可以怎样理解和改进？

### 最后扫描 26 个位置是正确的

先把所有需求都减完，再统一寻找负数，逻辑完全正确。因为固定只扫描 26 个位置，这一步是常数工作，不是性能瓶颈。

### 也可以在消耗时立即判断

某个位置第一次变成负数时，已经证明对应字母供不应求，后续字符无法把已经发生的缺口变成合法匹配。因此可以立即结束。这减少了不必要的后续扫描，但不改变总体线性复杂度。

### 长度是一个免费的必要条件

如果 `ransomNote` 比 `magazine` 更长，即使字母种类暂时未知，也不可能获得足够的字符总数，可以提前判定失败。不过长度足够并不代表一定成功，仍需检查每种字母的数量。

### toCharArray() 会创建副本

当前实现把两个 String 都转换成了 `char[]`。这样遍历很直观，但会额外创建与字符串长度相同的两个数组。

所以应区分：

```text
核心频次结构本身：O(26) = O(1)
当前完整实现（包含两个 char[] 副本）：O(m + n) 额外空间
直接从 String 逐位置读取：可以避免这两个副本
```

这不是逻辑错误，但在分析空间复杂度时不能忽略。

## 7. 与第 350 题的关系

两题维护的是同一个状态：

> 某一类元素还剩多少个可以使用。

共同过程：

```text
先统计供应
遇到需求或候选匹配时消耗一次
消耗后不能重复使用同一个元素
```

区别在于目标：

| 题目 | 扫描时关心什么 | 最终返回什么 |
| --- | --- | --- |
| 350 | 当前元素还有库存就完成一次匹配 | 所有成功匹配的元素 |
| 383 | 每个需求都必须有库存，出现缺口就失败 | 能否满足全部需求 |

因此 350 是“尽可能收集成功配对”，383 是“验证全部需求能否满足”。

## 8. 复杂度

设 `magazine` 长度为 `m`，`ransomNote` 长度为 `n`：

```text
时间复杂度：O(m + n + 26) = O(m + n)
频次表空间：O(26) = O(1)
```

如果把 `toCharArray()` 创建的副本也计算在内，当前写法的实际额外空间是 `O(m + n)`；不创建字符数组副本时，算法辅助空间才是固定的 `O(1)`。

## 9. 一句话总结

> 第 383 题把 magazine 看作 26 种字母的库存，把 ransomNote 看作必须全部满足的需求；库存减到负数，就证明某种字母供应不足。
