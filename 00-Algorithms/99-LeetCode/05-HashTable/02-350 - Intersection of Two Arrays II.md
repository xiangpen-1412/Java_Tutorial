# LeetCode 350：Intersection of Two Arrays II

> 难度：Easy  
> 主题：频次表、数组哈希、多重集合交集、库存消耗

## 1. 问题

给定两个整数数组，返回它们的交集。这里的“交集”必须保留能够在两边配对的重复次数，结果顺序任意。

对任意数字 `x`：

```text
x 在结果中的次数 = min(x 在 nums1 中的次数, x 在 nums2 中的次数)
```

例如：

```text
nums1 = [2, 2, 2, 3]
nums2 = [2, 2, 3, 3, 3]

2 最多配对 2 次
3 最多配对 1 次
结果可以是 [2, 2, 3]
```

题目的决定性条件还有：数组长度不超过 `1000`，元素范围固定为 `0～1000`。

## 2. 题型识别

这题属于：

```text
哈希思想下的频次统计
+ 多重集合（multiset）交集
+ 资源库存与消耗
```

识别信号不是只有“两个数组的交集”，更关键的是：

```text
结果中的元素要出现 as many times as it shows in both arrays
```

这说明只记录“出现过没有”不够，还必须记录“还能使用几次”。因此状态应当是频次，而不是普通 `HashSet` 的存在性。

## 3. 核心转换：从两张统计表变成一份库存

最直接的正确思路是分别统计两个数组，再对共同数字取较小频次。这正是最初使用两个 `HashMap` 的思路：

```text
nums1 frequency
nums2 frequency
共同 key 的结果次数取 min
```

问题在于，第二张完整频次表并不是必要信息。可以只把一边统计成库存，然后遍历另一边即时匹配：

```text
统计一边的次数，作为库存
遍历另一边：
    库存大于 0 → 匹配成功，记录结果，库存减 1
    库存等于 0 → 当前元素无法再匹配
```

例如先统计：

```text
库存：2 → 3，3 → 1
```

另一边依次出现 `2、2、3、3、3` 时：

```text
第一个 2：3 → 2，匹配
第二个 2：2 → 1，匹配
第一个 3：1 → 0，匹配
后续的 3：库存为 0，不匹配
```

这样在扫描第二个数组的同时，已经隐式完成了两边频次取最小值。

## 4. 核心不变量

扫描另一边的过程中，频次表始终表示：

> 被统计的那一边中，当前数字还剩多少个没有参与匹配。

因此：

- 频次大于 `0`，表示还可以消耗一次；
- 匹配后减一，保证同一个数组元素不会被重复使用；
- 频次等于 `0`，表示这一类数字已经全部配完。

这个不变量解释了为什么不需要第二张表，也解释了为什么每次成功匹配后必须减少频次。

## 5. 数据结构选择

### 当前题目：固定范围的计数数组

题目保证数字只在 `0～1000`，所以数字本身可以作为下标：

```text
frequency[x] = 数字 x 当前剩余的数量
```

这叫直接寻址，也常被称为数组哈希。它没有真正进行哈希计算，但承担了 HashMap 中 `key → frequency` 的同一职责。

相比 `HashMap<Integer, Integer>`，计数数组避免了哈希计算、节点对象以及 `Integer` 装箱、拆箱，常数开销更小。

### 数值范围大或未知：HashMap

如果数字可能非常大、为负数，或者范围无法接受，就不能按最大值开计数数组。此时仍复用相同的库存模型，只把频次表换成 `HashMap`。

如果使用 HashMap，优先统计较短数组，可以让可能保存的不同 key 更少。无论使用哪种结构，结果长度都不会超过较短数组的长度。

## 6. 与 349 的区别

```text
349：只关心某个数字是否同时存在，结果去重
350：关心某个数字可以配对多少次，结果保留重复数量
```

例如：

```text
nums1 = [2, 2]
nums2 = [2, 2, 2]

349 → [2]
350 → [2, 2]
```

所以：

```text
存在性、去重 → Set / boolean 状态
出现次数、可使用次数 → frequency
```

## 7. 复杂度与真正的优化点

两个数组都至少需要读取一次，因此线性扫描已经达到渐进意义上的最优：

```text
时间复杂度：O(n + m)
```

在当前固定数值范围下，计数数组的额外空间是：

```text
O(1001) = O(1)
```

最初的两个 HashMap 方案在平均意义上同样是 `O(n + m)`，所以优化不是把大 O 降得更低，而是：

```text
两张频次表 → 一张库存表
HashMap → 固定范围的直接寻址数组
装箱与 Stream 转换 → 更轻量的顺序处理
```

## 8. 变种与注意点

- 如果两个数组已经排序，可以使用双指针；相等时记录并同时前进，不相等时移动较小值的一侧。
- 如果一个数组远小于另一个数组，优先统计较小的一边；较大的一边可以顺序读取并即时匹配。
- 如果大数组存放在磁盘且无法全部载入内存，只要较小数组的频次表能放进内存，就可以流式读取大数组。
- 结果数组的最大可能长度是 `min(nums1.length, nums2.length)`，但实际长度要在匹配完成后才知道。

## 9. 我的思维误区

- **认为取两边频次的最小值就必须建立两张 Map**：第二边的频次可以在遍历过程中逐个体现；把第一边看作库存并即时消耗，就不需要完整保存第二张表。
- **只看 LeetCode 毫秒数判断算法是否优化**：两种方案的渐进时间都已经是线性，差异主要来自数据结构、装箱和结果转换的常数开销，单次运行时间本身也会波动。

## 10. 一句话总结

> 第 350 题不是判断“有没有共同元素”，而是维护每个数字的剩余库存；匹配一次就消耗一次，最终自然得到两边频次的较小值。
