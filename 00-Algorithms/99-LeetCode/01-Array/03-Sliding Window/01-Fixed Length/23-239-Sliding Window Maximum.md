# 239. Sliding Window Maximum

## 问题

给定整数数组 `nums` 和窗口长度 `k`，让一个**长度固定为 `k` 的连续窗口**从左到右每次移动一格，依次返回每个完整窗口内的最大值。若数组长度为 `n`，共有 `n - k + 1` 个完整窗口，因此结果数组也有这么多个元素。数组可以包含负数和重复值；要求的是每个窗口各自的最大值，不是整个数组的最大值，也不是所有窗口中的一个最优结果。[题目链接](https://leetcode.com/problems/sliding-window-maximum/description/)

本题已完成。本轮先检查了自己写的优先队列版本，再学习单调双端队列的推导和两端操作。

## 核心收获

### 固定窗口容易移动，难点是最大值不能像总和一样直接更新

当右端为 `right` 时，完整窗口是 `[right - k + 1, right]`。向右移动时，旧左端离开、新右端加入，边界没有歧义。

但只保存一个 `max` 不够：如果离开的元素正好是最大值，就无法从这个最大值反推出剩余元素的最大值。与 [[09-643-Maximum Average Subarray I]] 的总和可以“减去旧值、加上新值”不同，本题需要保留足够的候选信息。

### 优先队列可以做：存下标、按对应数值维护大顶堆

我的堆方案存储的是下标，比较的是 `nums[index]`。这样堆顶能提供当前保存元素中的最大值，同时又能根据下标判断它是否已离开窗口。

```text
当前窗口左端：left = right - k + 1
过期条件：   queue.peek() < left
答案：       nums[queue.peek()]
```

在读答案之前，不断弹出过期堆顶，直到堆顶有效。这是“惰性删除”：过期元素如果还在堆内部，可以暂时不删；它没有挡住当前有效最大值，以后若成为堆顶，再检查并移除即可。新下标可以在清理之前或之后加入，只要取答案时堆顶已通过有效性检查。

堆的正确性不要求内部只剩当前窗口元素，但这会影响空间和时间：例如严格递增的数组、`k = 2` 时，新值始终成为堆顶，旧的小值会一直埋在内部，堆可以增长到 `n`。因此这种写法的最坏时间是 **`O(n log n)`**、额外空间是 **`O(n)`**，不能因为窗口只有 `k` 个元素就自动写成 `O(n log k)`、`O(k)`。

### 单调双端队列：淘汰被更新且不小的元素取代的候选

堆保留的信息仍然偏多。假设旧下标为 `old`，新下标为 `right`，满足：

```text
old < right
nums[old] <= nums[right]
```

新元素**不小于旧元素，而且比它更晚过期**。从现在起，只要某个后续窗口还包含旧元素，它也一定包含更新的这个元素；旧元素永远无法提供更大的最大值。因此可以永久淘汰旧候选，而不用等它过期。

即使两者数值相等，也可以只保留更靠右的那个：它提供相同的值，却能留在窗口里更久。

用双端队列保存剩余候选的下标，并维持三个性质：

- **下标从队首到队尾递增**，所以最早过期的候选在队首。
- **对应数值从队首到队尾严格递减**，所以最大值在队首；这里使用 `<=` 作为弹尾条件。
- **输出答案时，队列里的下标都在当前窗口内**，过期候选已经从队首清除。

每次新值加入时，从队尾连续淘汰所有不大于它的候选，再将新下标放入队尾。一个新值可能同时淘汰多个旧候选，因此这里用 `while`。

### 队列保存的是候选，不是窗口全部元素

窗口 `[1,3,1]` 内有三个元素，但候选队列只需要保存下标 `1:3`、`2:1`。最前面的 `0:1` 被后来更大的 `1:3` 淘汰，完全不影响结果。

因此，不能把队列长度当成窗口长度，也不能通过“队列满了 `k` 个就删一个”来判断过期。**窗口边界由数组下标决定；队列长度由哪些元素仍值得保留决定。**

### `Deque` 是容器，两端操作由算法分工

之前我主要把 `Deque` 当成栈或普通先进先出队列使用。这题用到了它的完整能力：同一个容器可以从两端查看、移除元素，不必固定成一种栈或队列策略。

Java 中可用 `Deque<Integer> deque = new ArrayDeque<>();` 保存候选下标。`ArrayDeque` **不会自动排序或维持单调性**，这些性质来自下面的操作规则：

| 操作 | 本题中的职责 |
| --- | --- |
| `peekFirst()` | 查看最靠前的候选下标；判断过期，或读取最大值 |
| `pollFirst()` | 从队首删除已经离开窗口的候选 |
| `peekLast()` | 查看队尾候选是否已被新值取代 |
| `pollLast()` | 从队尾删除已被新元素取代、不再需要保留的候选 |
| `offerLast(right)` | 将新下标加入队尾 |

这两类删除的理由不同：**队首删的是过期元素，队尾删的是仍可能在窗口内、但已没有保留价值的元素。** 删除队尾候选不意味着移动窗口左端。

保留每轮结构即可还原实现，不需要重新扫描整个窗口：

```java
while (!deque.isEmpty() && deque.peekFirst() < right - k + 1) {
    deque.pollFirst();
}
while (!deque.isEmpty() && nums[deque.peekLast()] <= nums[right]) {
    deque.pollLast();
}
deque.offerLast(right);
if (right >= k - 1) {
    res[right - k + 1] = nums[deque.peekFirst()];
}
```

### 用原来的失败例子核对全过程

`nums = [1,3,1,2,0,5]`、`k = 3`。下面的队列用“下标:值”表示，每行都是处理当前元素后的状态。

| `right` | 本轮关键变化 | 候选队列 | 完整窗口的最大值 |
| ---: | --- | --- | ---: |
| 0 | 加入 `0:1` | `[0:1]` | 窗口未满 |
| 1 | 新值 `3` 淘汰队尾 `0:1` | `[1:3]` | 窗口未满 |
| 2 | 新值 `1` 保留在队尾 | `[1:3, 2:1]` | 3 |
| 3 | 新值 `2` 淘汰队尾 `2:1` | `[1:3, 3:2]` | 3 |
| 4 | 左端变为 `2`，队首 `1:3` 过期 | `[3:2, 4:0]` | 2 |
| 5 | 新值 `5` 依次淘汰 `4:0`、`3:2` | `[5:5]` | 5 |

输出为 `[3,3,2,5]`。`right = 4` 时虽然最大值 `3` 已经离开，队列仍保留了下一个有用候选 `3:2`，无需重新扫描窗口 `[1,2,0]`。

### 为什么嵌套 `while` 仍然是线性时间

每个下标只会入队一次。入队后，它可能从队尾被新值淘汰，或以后从队首因过期被移除；一旦出队就不会回来，所以每个下标最多出队一次。

某一轮可能弹出很多元素，但所有轮次加起来的出队次数最多为 `n`。因此总时间为 **`O(n)`**；队列只保存当前窗口内的候选，最多 `k` 个，额外空间为 **`O(k)`**。

| 方法 | 保留、处理的信息 | 最坏时间 | 额外空间，不含输出 |
| --- | --- | --- | --- |
| 每个窗口重新扫描 | 逐个查看窗口全部元素 | `O((n-k+1)k)` | `O(1)` |
| 惰性删除的大顶堆 | 所有尚未从堆顶清理的元素 | `O(n log n)` | `O(n)` |
| 单调双端队列 | 未过期且仍可能成为最大值的候选 | `O(n)` | `O(k)` |

## 变种与注意点

- **完整窗口从 `right = k - 1` 开始。** 对应的结果位置为 `right - k + 1`，第一个是 `0`，最后一个是 `n - k`。前面的元素也照常维护候选，但还不能输出长度不足 `k` 的窗口。
- **过期条件有两个等价写法。** `index < right - k + 1` 等价于 `index <= right - k`。等于当前左端的下标仍然有效，不能提前删除。
- **存下标同时解决位置和值的问题。** 用下标判断是否过期，再通过 `nums[index]` 比较值；重复值也能区分各自的离开时间。
- **弹尾用 `<` 也能正确求最大值，但会保留相等候选。** 本笔记统一使用 `<=`，保留更新的等值元素，候选值严格递减。不要把两种写法对应的“严格递减”和“非递增”不变量混淆。
- **负数不破坏本题方法。** 比较候选大小和先后位置即可，不依赖元素非负。`k = 1` 时结果就是每个元素本身；`k = n` 时只输出整个数组的一个最大值。
- **求窗口最小值时，淘汰方向相反。** 较小且更新的元素可以取代较大的旧候选。1438 也涉及窗口极值，但窗口长度由合法性条件决定；这里的候选维护思路可以迁移，窗口边界规则还要重新分析。

## 我的思维误区

### 已存下标，却没有让过期判断跟随窗口移动

我的优先队列代码让 `left = 0` 一直不变，并用 `peek < left + 1` 判断过期。窗口第一次移动时，左端恰好是 `1`，看起来还能工作；后续却始终只排除下标小于 `1` 的元素。

在 `[1,3,1,2,0,5]`、`k = 3` 中，`right = 4` 时实际窗口已经是 `[2,4]`。下标 `1` 的 `3` 应当移除，却仍留在堆顶，因此结果变成 `[3,3,3,5]`，而正确结果是 `[3,3,2,5]`。

下次先根据固定长度写出 `left = right - k + 1`，再判断 `peek < left`。堆和单调队列都不能替我推断窗口边界，边界必须由代码明确维护。原先的 `peek > right` 检查则没有实际作用，因为队列只加入已经扫描到的下标，不会出现未来位置。

### 用 `0` 初始化首窗最大值，默认了答案不能为负数

我的首窗计算从 `max = 0` 开始，但本题允许负数。例如 `nums = [-2,-1]`、`k = 2`，正确答案是 `[-1]`，这种初始化却会得到 `[0]`，返回了窗口里不存在的值。

若保留单独计算首窗的写法，应从实际元素或 `Integer.MIN_VALUE` 初始化；既然已经建好了大顶堆，也可以直接读取 `nums[queue.peek()]`。单调队列统一在窗口完整后读取队首，也就不需要另设一个默认首窗最大值。
